# 开发待办

以下只记录尚未完成的可靠性优化，按建议实施顺序排列。

## 1. 异常退出后的消息恢复

当前从控制台停止、重启或退出时，Bridge 会先处理防抖窗口内的消息，并等待已提交的 Supabase 写入完成。突然断电、系统崩溃或进程被强制结束时，尚未处理的消息仍可能丢失。

- [ ] 将待处理的防抖批次持久化到 SQLite。
- [ ] 将尚未完成的 Supabase 写入持久化为可重放任务。
- [ ] Bridge 启动时恢复未完成任务，并继续处理。
- [ ] 结合已处理事件收据保证恢复后不会重复回复或重复写入。
- [ ] 覆盖断电模拟、处理中崩溃、恢复重放和失败后重试测试。

## 2. Supabase 总结版本原子化

当前总结版本采用“读取最大版本后加一”。两台电脑同时为同一会话生成总结时，可能写入相同版本并发生竞争。

- [ ] 增加 Supabase RPC 或数据库函数，在数据库内原子分配版本并写入总结。
- [ ] 为迁移脚本补充升级说明和 schema cache 刷新步骤。
- [ ] 验证两个 Bridge 同时总结时不会冲突、覆盖或丢失结果。
- [ ] 明确 RPC 缺失或权限错误时的日志和降级行为。

## 3. 分阶段延迟日志

当前日志不足以直接判断慢在防抖、记忆、模型还是 QQ 发送阶段。

- [ ] 分别记录防抖等待、上下文读取、回复判断、模型调用和 NapCat 发送耗时。
- [ ] 记录单次批处理总耗时、消息数量和会话标识，避免记录聊天正文和密钥。
- [ ] 为慢请求增加清晰的阶段标记，便于从控制台定位瓶颈。
- [ ] 增加计时字段和日志格式测试。
